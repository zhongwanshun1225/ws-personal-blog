## 我在做什么

主要做 Web 全栈开发。日常打交道最多的是 TypeScript、Node.js 和 PostgreSQL，最近两年花了不少时间在**工程效率**上——构建速度、调试体验、代码可维护性这些不太性感但很实在的事情。

我判断一个技术方案的标准很朴素：

1. **上线三个月后还愿意看它的代码吗？**
2. **新人接手需要多久才能改出第一个 bug fix？**
3. **出问题的时候，日志能不能告诉我发生了什么？**

三个问题里有两个答不上来，我就会重新考虑。

## 我的技术偏好

- 倾向于**少即是多**。能用标准库解决的不引库，能用 20 行解决的不引框架；
- 相信**可观测性**比微服务架构更重要。见过太多系统拆得很漂亮，出了问题却查不出原因；
- 对"手写 SQL"没有偏见。ORM 很好，但它不该成为你不理解索引的借口；
- 认为**文档和注释是代码的一部分**，而不是"有时间再补"的选项。

> [!NOTE]
> 这些偏好会随着踩坑变化。如果你在几年前的代码里看到相反的写法，那说明我成长了——而不是当时的我错了。

## 关于这个博客

用 Markdown 写、静态生成、托管在 GitHub Pages。没有评论系统，没有访问统计，也没有花哨的动效。

写在这里的东西大致分三类：

| 类型 | 说明 | 例子 |
| --- | --- | --- |
| 踩坑记录 | 真实遇到过的问题，附完整解法 | 《PostgreSQL 索引没生效？先排查这 6 个原因》 |
| 方案权衡 | 面对多个选项时的判断依据 | 《前端性能优化：按收益排序的 12 条清单》 |
| 项目复盘 | 做过的项目，包括失败的部分 | 《汉字笔顺练习》 |

**我不写"从入门到精通"**。那种内容网上已经足够多，我写不出更好的。我只写那些"当时找遍全网也没找到确切答案"的东西。

## 如何联系

- 有问题欢迎在 GitHub 上开 Issue，我通常两天内回复；
- 邮件也行，但回复会慢一些；
- 如果想要某个具体问题的排查思路，附上 `EXPLAIN` 输出或者最小复现，会大大加快沟通效率。

## 一些不变的东西

写博客这件事我已经断断续续做了很多年，中间停过两次，每次都被"没有反馈"劝退。后来想明白了一个道理：

> **写作的第一读者永远是自己。** 如果一篇文章能让半年后的我少花两小时，它就已经值回票价了。

所以这次不设 KPI，不看访问量，只求持续记录。
