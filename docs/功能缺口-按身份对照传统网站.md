### 5.1 工程化

| # | 缺口 | 说明 | 优先级 |
| --- | --- | --- | --- |
| E2 | **前端无错误上报** | 线上 JS 报错静默失败，用户遇到的 bug 你永远不知道（`analytics.js` 只上报访问量，不上报异常） | P1 |
| E3 | **无 lint / format** | Python 无 ruff / black，JS 无 eslint / prettier，也无 `.editorconfig` | P2 |
| E5 | **3 个云端函数未版本化** | `post_interaction` / `admin_list_emails` / `is_admin` **只存在于线上库，`cloud/sql/` 里没有定义**。重建一次数据库这三个就没了，而 `is_admin()` 是 40+ 个 RPC 的身份闸门、`post_interaction()` 供文章页读互动数据 → 连带整体瘫痪 | P1 |

> 本轮已闭环：**E1 测试进 CI**。原先的探针散在 `.preview/`（**该目录在 `.gitignore` 内，CI 里根本拿不到**），
> 现已迁移为被追踪的 `tests/`：**16 个探针、766 项断言**（idle 23 / auth 16 / comment-thread 11 / mirror-redirect 13 /
> ws-backup 27 / backup-panel 26 / build-cache 31 / chrome-noise 20 / dist-clean 4 / page-transition 37 /
> batch3-smoke 54 / batch4 54 / batch6 150 / batch7 242 / guest 58；batch3-notify-render 需 Chrome，无浏览器时跳过）。
> - 单一入口 **`tests/run-tests.mjs`**：逐个跑子进程、逐行转发 PASS/FAIL、末尾汇总表，
>   用 `process.exit(failed ? 1 : 0)` 把失败**真实传出去**（此前探针即使 FAIL 也常常退出码 0）；
>   加新探针只需往 `SUITES` 数组里加一行，不用改 workflow。
> - workflow 在 **Build 之后**加 `node tests/run-tests.mjs` 一步（探针读的是 `dist/` 产物，顺序不能反）。
> - 依赖无头 Chrome 的断言**找不到浏览器时自行 SKIP 且不影响退出码** —— 本沙箱起不了 Chrome，
>   但 CI 的 `ubuntu-latest` 上能跑满；本地不装 Chrome 也不会假红。
> - `tests/_serve.mjs` 抽出共享工具：`startStaticServer()` 起只读 dist 静态服务，
>   `probeChrome()` 做**真·可用性探测**（真跑一次 `--headless=new --dump-dom data:text/html,<body>ok</body>`
>   并要求拿到含 `<body` 的输出，带 25s 超时兜底），而不是只判路径存在 —— 这是本地也能全绿的关键。
> - `tests/.gitignore` 排除 `.chrome-*/`（无头 Chrome 的临时用户目录，不排会累积上百 MB）；
>
> 本轮另已闭环：**E4 构建产物缓存**（两层，互不耦合）：
> 1. **产物写入去重**（`build.py::write()` / `copy_file()`）—— 落盘前先比对目标文件，
>    内容逐字节相同就**跳过这次写入**，并统计「跳过 / 写入 / 省下字节」。实测全量重建命中
>    **约 97%（126/130）**，省约 5.7 MB 写入。**关键设计**：HTML 即使命中也要照跑
>    `check_nested_anchors` —— 它校验的是「源码有没有嵌套锚点」，与内容是否变过无关，
>    跳过校验会让一次缓存命中**掩盖住新引入的缺陷**。
>    刻意**不做**「按源文件 mtime 跳过整页渲染」那种大缓存：本站全量构建约 20s，按 mtime 判断
>    会把「改了一处 CSS 影响全站」这类跨文件依赖判错，得引入完整依赖图才安全，收益不抵复杂度。
>    这里只做**写入层去重** —— 行为可预测、零依赖图，对增量与全量构建都安全。
> 2. **构建期云端响应缓存**（新增 `wsblog/cloudcache.py`，默认 **TTL 300 秒**）——
>    在 `cloudposts.py` / `cloudsettings.py` / `cloudstats.py` 三个取数模块的**唯一漏斗**处按 URL
>    缓存响应（settings 的 key 还带上 POST body）。实测第二次构建从 **38.9s 降到 2.2s**（省 30–36%）。
>    ⚠️ **`cloud_posts_fingerprint()` 刻意不缓存** —— 它是**变化检测器**，缓存等于废掉热重建。

  以及**登录页自身必须排除**（否则刚打开登录页就被计时）。
- **本地全绿 ≠ 能上生产（三条实测教训）**：
  1. **本地 Python 新 ≠ 沙箱 Python 新**。PEP 701（3.12+）之后 f-string 替换字段里允许写 `#` 注释，
     本地（3.13.12）一路构建通过，沙箱解析阶段就 `SyntaxError`，而报错表现为
     `service did not become reachable on port 3000 within 60s`（真错在 stderr 的 traceback 里）。
     **发布前跑 `.preview/check-py-compat.py`**（退出码 0 = 干净）。注意 `ast.parse(..., feature_version=(3,11))`
     **抓不到**这类问题，别拿它当兼容检查；`#` 在 f-string 字面量部分（CSS `#fff`）是合法的，也别简单 grep `#`。
  2. **CI 拿不到 `.preview/`**。该目录在 `.gitignore` 内 —— 所以在 workflow 里写 `node .preview/xxx.mjs` 必然失败。
     E1 已把探针迁进被追踪的 `tests/`，**以后新增探针一律放 `tests/`**。
  3. **冒烟测试留下的 Chrome 临时目录会拖垮发布**。`sites` 发布打包整个工作区（仅排 `node_modules`/`.git`/构建产物），
     `.preview/` 与 `tests/` 下累积的 `.chrome-*` 目录曾涨到 1.5GB → 上传包 252MB → 沙箱解压 502。
     **跑完立即 `mv` 走**（同盘 mv 秒完成；`rm` 会被 safe-delete 钩子转 genie-trash 且传 MSYS 路径必失败）。
- **worker（定时云函数）的三条硬约束（第八批 B5 实测）**：
  1. **REST 通道 `/.cloud/database/rest/rpc/` 的服务端调用身份就是 `anon`** —— 云函数没有用户 JWT。
     所以 worker 用的 RPC 写成 `REVOKE ... FROM anon` 会让 worker 拿到 `401 permission denied`
     （`backup_worker_config` 首次调用即撞上）。**正确做法是 `GRANT EXECUTE ... TO anon`，
     安全边界靠函数体第一段的共享密钥校验**（密钥不对一律返回 forbidden）。`notify_*` 三个 worker RPC
     线上本来就是这个授权，源码里曾写成 REVOKE，已补齐。
  2. **storage 写接口与数据库 REST 鉴权方式不同**：只带 `x-wb-webapp-access-key` 会被拒
     （`401 MISSING_CREDENTIALS`），前端 SDK 是 `x-wb-webapp-access-key` + `Authorization: Bearer <匿名令牌>`
     **两个头**并用（令牌来自 `vendor/cloud-sdk.js` 的 `anonymousTokenProvider`）。
     ⚠️ 但架构上**本站存储不适合当备份去向** —— 同一朵云、同一个环境、同一个桶，
     云环境整块丢失就一起没。B5 因此把「本站留存」默认关闭（`BACKUP_STORE_LOCAL`），
     让「异地」（Webhook / S3）成为唯一真实的副本去向。
  3. **`auth.users.id` 是 `bigint` 不是 uuid**；与 `public.profiles.owner_id`（text）靠 `au.id::text = p.owner_id` 关联。
- **构建缓存的两条复核要点（第九批 E4 实测）**：
  1. **比对产物一致性时先排除「时间戳文件」** —— `assets/build-info.json`（`generatedAt`）、
     `assets/slug-manifest.json`、`feed.xml`（`lastBuildDate`）、`search-index.json` 每次构建都会变，
     与缓存无关。判据是：若 `--clean` 与 `--no-cloud-cache` 两种构建的差异集合**完全相同**，
     那就是时间戳而非缓存 bug。排除这 4 个后本站 **126 个产物逐字节一致**。
  2. **改缓存必须先看发布路径**：`sites_deploy` 打包整个工作区（`.preview/` 在内），
     所以任何落在 `.preview/` 的缓存都可能被带进沙箱。现由 `--serve` 调
     `cloudcache.mark_serve_mode()` 硬禁用兜住 —— 复核缓存改动时**先确认这条防线还在**。
- **演示数据（2026-10-15 注入）**：云端现有 4 位演示作者（`profiles.owner_id` 为
  `9900000000000000001..04 / ...09` 段）+ 7 篇云文章（含定时 / 待审 / 草稿各态）+
  15 条评论（含待审与被隐藏的垃圾评论）+ 372 条 PV + 订阅 / 通知 / 审计 / 媒体 / 修订 / 备份各若干。

## 附 2. 本地验不到的部分

云端按 Origin 只放行 `https://ws-blog.app.workbuddy.host`，本地 `127.0.0.1` 上
登录 / 评论 / 投稿 / 后台全部 403。所以「点通过、点驳回、批量删除、生成预览链接、开 2FA、
执行导出」这类交互**必须到线上手测**，本地只能验证构建产物与静态页面。

⚠️ 另一个容易误判的点：**`admin.html` / `write.html` 在本地做 DOM 快照拿到的是登录页** ——
`cloud.js` 的 `guardAdmin()` 在无会话（本地必然无会话，因为 RPC 被 403）时
`location.href = login.html`，所以 `--dump-dom` 出来的不是后台结构。这是**预期行为，不是缺陷**。

本地能验的是：模板元素是否齐全、脚本是否挂上、文案键是否写错、JS 是否报错 ——
`tests/` 下 16 个探针（**766 项断言**）覆盖这些；其中依赖无头 Chrome 的 DOM 断言
在浏览器不可用时**自行 SKIP 且不影响退出码**（本沙箱起不了 Chrome，CI 的 ubuntu-latest 上能跑满）。
用无头 Chrome 扫页面 console 时（**只认带 `CONSOLE(` 标记的页面报错**，
Chrome 自身的 Extension / GCM / updater / named-pipe 日志不算）。

⚠️ **本地也验不到「管理员身份下」的服务端行为**：MCP 查库的每次调用都是独立会话，
`set_config('request.jwt.claim.sub', ...)` 留不下来，**无法模拟管理员**去测 `is_admin()` 守卫的 RPC
（`admin_backup_status` / `admin_backup_setting` 等）。这类只能线上手测。
