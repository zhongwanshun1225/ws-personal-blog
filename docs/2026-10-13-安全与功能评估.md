# WS Blog · 安全与功能评估

> 评估时间：2026-10-13  
> 评估方式：通读 11 个前端脚本、9 个 Python 模块、页面模板；直连云数据库核对 7 张表的字段类型、约束与全部 RLS 策略、8 个 SECURITY DEFINER 函数的实际定义；并用无头 Chrome 对关键漏洞做了实证复现。  
> 与 `全盘扫描-功能缺口与技术闭环.md` 的关系：那份文档的 3 个 P0 断点（云文章合流、图片上传、评论楼中楼+PV）**已经全部落地**，本文不重复；本文的重点是安全逻辑（上一版仅 4 条泛化条目）与合流之后新暴露的问题。

## 0. 结论摘要

| 维度      | 判断                                                                                                   |
| ------- | ---------------------------------------------------------------------------------------------------- |
| 架构与边界设计 | **良好**。权限的真正边界在数据库（RLS + SECURITY DEFINER），前端守卫只做体验；「管理员身份」只存 localStorage、不影响服务端判定，拿不到额外权限。这个分层是对的。 |
| 前端输出转义  | **到位**。所有 innerHTML 拼接点都过了 `escapeHtml`，未发现靠 `author_name`/标题/昵称的常规注入。                               |
| 内容净化    | **有一个可直接利用的高危缺陷**。`sanitize` 是黑名单式，且 `decorate` 在其之后用 `innerHTML` 二次解析，把已清理的标签"复活"。已实测：零点击存储型 XSS。   |
| 服务端写入校验 | **偏薄**。评论的 `author_name`、`status`、长度、`parent_id` 归属全部由客户端说了算。                                        |
| 资源与滥用防护 | **缺失**。浏览量接口无鉴权、无节流、可写任意 slug；无任何频率限制；无长度上限。                                                         |
| 可观测性    | **缺失**。管理动作无审计日志；无前端错误上报；无访问分析。                                                                      |
| 内容时效闭环  | **有断点**。云文章合流只在构建期发生，发布后不触发重建，搜索/RSS/sitemap 会陈旧。                                                    |

## 1. 安全问题（按可利用性排序）

### 1.1 [P0，已实证] 存储型 XSS：callout 二次解析绕过净化，普通用户可打到管理员

**位置**：`src/scripts/cloud-markdown.js`

```js
// renderMarkdown()  第 211–223 行
holder.innerHTML = marked.parse(source, { gfm: true, breaks: false });
sanitize(holder);      // ① 先净化
decorate(holder);      // ② 之后又插入一次未净化的 HTML
return holder.innerHTML;
```

```js
// decorate() 的 callout 分支  第 139–141 行
var rest = match[2];                       // 来自 first.textContent —— 实体已被解码
var rebuilt = window.marked.parseInline(rest);
first.innerHTML = rebuilt;                 // 二次解析，完全绕过 ①
```

`sanitize()` 是黑名单式（删 `script/iframe/object/embed/style/link/meta/base` 标签，删 `on*` 属性与 `href/src` 上的 `javascript:`）。它挡得住直接写 `<img src=x onerror=...>`，但挡不住下面这条链路：

1. 作者写一个提示块，里面放**HTML 实体**（`&lt;img …&gt;`），marked 输出时仍是实体，DOM 解析后 `textContent` 变回真实的 `<img …>`；
2. `decorate` 用 `parseInline` 重解析这段文本（marked 默认透传原始 HTML），再 `innerHTML` 赋回 → 一个**从未经过 `sanitize`** 的 `<img onerror=…>` 出现在返回值里；
3. 调用方把这个字符串赋给真实 DOM（`admin.js` 第 327、610 行的审核预览；`cloud-posts.js` 第 174 行的文章正文），`onerror` 立即执行 —— **无需任何点击**。

**实测证据**（`.preview/xss-probe.html`，无头 Chrome 复现）：

- 输入 `> [!TIP]` + `> &lt;img src=x onerror="document.title='PWNED-A'"&gt;`
- `render()` 返回值中 `onerror` 原样保留 → 挂入真实 DOM 后 `document.title` **由 `SAFE` 变为 `PWNED-A`**

**为什么这条最严重**：投稿是开放的（任何注册用户都能投）。攻击者投稿一篇带载荷的文章 → 管理员在后台点「查看」→ 载荷在**管理员的会话里**执行 → 可调用 `admin_review_post` / `admin_set_user_status` / `admin_delete_user` / `admin_add_email`（这些函数只认 `is_admin()`，而此刻正是管理员的身份）→ **普通用户一步提权为站长**。文章一旦通过审核，所有访客也会中招。

`form action="javascript:"` 与 `button formaction="javascript:"` 同样能穿过 `sanitize`（属性名单里没有 `action`/`formaction`），实测亦保留在返回值中——这是同一个根因的另一个入口。此外 `<form action="https://evil.example">` 能做出**以假乱真的站内登录框**，把读者输入的邮箱密码直接投递到攻击者服务器，这条路不依赖任何 JS。

**修复建议（按优先级）**

1. **去掉二次解析（最小改动，立刻能上）**：不要用 `parseInline` 重建 callout 首段，改为在已净化的 DOM 上删掉开头那段 `[!TIP]` 文本前缀，保留其余子节点结构：
   ```js
   // 取代 first.innerHTML = rebuilt;
   var label = /^\[!(NOTE|TIP|IMPORTANT|WARNING|CAUTION)\]\s*/i.exec(first.textContent);
   if (label) {
     var walker = document.createTreeWalker(first, NodeFilter.SHOW_TEXT);
     var node;
     while ((node = walker.nextNode())) {
       if (node.nodeValue.indexOf('[' + label[1] + ']') >= 0) {
         node.nodeValue = node.nodeValue.replace(/^\[!(NOTE|TIP|IMPORTANT|WARNING|CAUTION)\]\s*/i, '');
         break;
       }
     }
   }
   ```
   （顺带解决了"标点/表情夹在标记与正文之间时被整段重建"的展示问题。）
2. **净化改为白名单**：引入 DOMPurify 本地化到 `src/vendor/`（与 marked/highlight 同样处理，不依赖 CDN），`render` 出口统一过一遍白名单。
3. 若暂时保留黑名单，至少补齐：`action`、`formaction`、`xlink:href`、`srcset`、`poster`、`ping`、`background`、`data-*` 中的 URL 属性，并把 `form`/`input`/`button` 一并从内容区禁用。
4. 加 `<meta http-equiv="Content-Security-Policy">` 兜底（见 1.6）。

### 1.2 [P0] 评论的 `author_name` 由客户端填写，可仿冒任意身份

**位置**：`src/scripts/interact.js` 第 382–387 行

```js
var payload = {
  post_slug: slug,
  content: content,
  author_name: (profile && profile.nickname) || C.displayName() || '读者',
};
```

云端的 `comments_own_all` 策略只校验两件事：

```
USING      (owner_id = auth.uid())
WITH CHECK (owner_id = auth.uid() AND is_active())
```

`author_name`、`status`、`content` 长度、`parent_id` 的归属**都没有约束**。这意味着任何登录用户都可以：

- 用 SQL/REST 直接插入 `author_name = 'WS'`（或管理员的昵称）→ **以站长名义发言**，评论区无法分辨；
- 插入任意长度正文（前端只限 1000 字，绕过前端即无上限）→ 撑爆页面、放大存储；
- 插入 `parent_id` 指向**别的文章的评论**或任意 id → 制造跨文章串楼、把回复挂到他人楼下；
- 指定 `status`（若表默认是 `visible`）→ 评论即时公开，没有待审环节，与投稿的严格审核形成明显反差。

**修复建议**

- 用 `BEFORE INSERT/UPDATE` 触发器把 `author_name` 强制为 `profiles.nickname`（或直接把该列从客户端可写集合里去掉，改由视图派生）：
  ```sql
  CREATE OR REPLACE FUNCTION public.comments_stamp_author() RETURNS trigger
  LANGUAGE plpgsql SECURITY DEFINER SET search_path TO 'public' AS $$
  BEGIN
    SELECT NULLIF(btrim(nickname), '') INTO NEW.author_name
      FROM public.profiles WHERE owner_id = auth.uid()::text;
    NEW.author_name := COALESCE(NEW.author_name, '读者');
    RETURN NEW;
  END $$;
  ```
- 加数据库级长度与取值约束：`CHECK (char_length(content) BETWEEN 1 AND 1000)`、`CHECK (status IN ('visible','hidden','pending'))`。
- 加 `CHECK` 或触发器校验 `parent_id` 必须属于**同一 `post_slug`** 且自身是顶层评论（防止楼中楼无限嵌套与跨楼）。
- 若希望评论区也走审核，把默认值改为 `pending`，并在 `post_comments` 里对作者本人放行（`status='visible' OR owner_id = auth.uid()`）。

**附带发现**：`comments.parent_id` 的外键是 `ON DELETE CASCADE`。作者删掉自己的一条评论时，**挂在他下面的别人回复会被一起静默删除**（`interact.js` 第 340 行的确认框只说"确定删除这条评论吗"）。建议改成 `ON DELETE SET NULL`（配合已有的孤儿修复逻辑），或在删除前明确提示"将同时删除 N 条回复"。

### 1.3 [P0，需一次性验证] 上传接口没有服务端类型白名单

**位置**：`src/scripts/upload.js`

前端只校验了 `accept`、`maxMB` 和 `file.type` 前缀：

```js
if (file.type && opts.accept === 'image/*' && file.type.indexOf('image/') !== 0) { ... }
```

`file.type` 来自浏览器、完全可伪造，服务端没有扩展名/MIME 白名单，路径由客户端拼（`blog/202610/<随机>.html` 也是合法路径）。若 bucket 允许任意类型且 `getPublicUrl` 返回**与站点同源**的地址，则上传一个 `.html`（或 `.svg`）再用公开 URL 打开，就是一个**同源存储型 XSS**：可读取 `localStorage` 里的会话令牌、伪装成站点发起请求，管理员若在这个页面登录过，等于账号被接管。

**建议先做一次性验证**：用一个已登录账号尝试上传 `t.html`（内容为 `<script>document.title='x'</script>`），拿到公开 URL 后访问，看是否被当作 HTML 渲染、以及地址是否与站点同源。

**修复建议**

- 服务端（存储策略/规则）限定 bucket 只接受图片扩展名与图片魔数；
- 前端读取文件头做魔数校验（`FF D8 FF` / `89 50 4E 47` / `RIFF…WEBP`），不信任 `file.type`；
- 若必须允许 SVG，则强制 `Content-Disposition: attachment` 或放到独立域名。

### 1.4 [P1] 浏览量接口无鉴权、无节流、可写任意 slug

**位置**：云端函数 `post_view`

```sql
INSERT INTO public.post_views (post_slug, views) VALUES (p_slug, 1)
ON CONFLICT (post_slug) DO UPDATE SET views = post_views.views + 1, updated_at = now()
```

- 函数是 `SECURITY DEFINER`，**没有做任何身份校验**，匿名即可调用；
- `post_views.post_slug` 是主键但**没有外键**，`p_slug` 想写什么就写什么 → 可以用随机 slug 灌入海量行，做**存储膨胀 / 统计污染**；
- 前端 `interact.js` 的 `countView()` 每次页面加载都调一次，**没有 sessionStorage 去重**，刷新即 +1。

叠加效果：浏览量数据没有参考价值，且可被用来撑表。`admin_stats` 里的 `views` 是对该表求和，会直接失真。

**修复建议**：加 `CHECK`/外键把 `post_slug` 限定在已存在的文章；函数内做节流（按 `auth.uid()` 或 IP 哈希 + 时间窗，或前端按 `sessionStorage` 去重 + 服务端最小间隔）；把浏览量并入构建期统计而非实时自增。

### 1.5 [P1] 列级信息泄漏：审核理由、审核人、作者 uid 对匿名可见

**位置**：策略 `posts_public_read`（`cloud_posts`）

```
USING (status = 'published')
```

RLS 是**行级**的，不区分列。任何匿名访客都能 `SELECT *` 拿到已发布文章的**全部字段**，包括：

- `review_note` —— 管理员给作者的驳回/内部备注（若通过时未清空则残留）；
- `reviewed_by` —— 审核人的 uid；
- `author_id` —— 作者 uid。

前端 `cloud-posts.js` 只 select 了少数字段，但 REST 接口可以任意指定 `select=`。同类问题还有：

- `profiles_read_all USING (true)` → 匿名可枚举**所有**用户的 uid / 昵称 / 头像 / 简介 / `status`（含谁被禁用了）；
- `post_likes.likes_read_all USING (true)` → 匿名可枚举"谁给哪篇文章点了赞"，配合上面的 profiles 就是一份行为画像。

个人博客里这些不算致命，但"审核理由"和"谁被禁用"属于不该公开的运营信息。

**修复建议**：把公开读取改成**视图**（只暴露 `slug/title/summary/tags/content_md/published_at`），把 `cloud_posts` 的 `posts_public_read` 从公开读降为仅作者 + 管理员；`profiles` 同理，公开视图只给 `nickname/avatar_url/bio`。

### 1.6 [P1] 缺少安全响应头，且当前结构难以收紧

`layout.py` 的 `<head>` 里没有 CSP、没有 `X-Frame-Options`、没有 `Referrer-Policy`。站点可以在任意站点被 iframe 嵌入（**点击劫持**），也缺少 XSS 的第二道防线。

难处在于页面里有三处内联脚本（`THEME_BOOT`、镜像跳转、`window.__ROOT__`），直接上严格 CSP 会把这些一起拦掉。

**务实建议（分批）**

1. 先加伤害面最小的一条（**meta 无法覆盖 `frame-ancestors`，需在托管侧加响应头**，或用一行 JS 做 frame-busting 兜底）：
   ```html
   <meta http-equiv="Content-Security-Policy"
         content="base-uri 'none'; form-action 'none'; object-src 'none'; img-src 'self' data: https:; frame-src 'none'">
   ```
   这几条不改动现有脚本即可生效，且正好把 1.1 里的 `<form action>` 钓鱼路径堵死。
2. 把三处内联脚本的**哈希**算出来，逐步换成 `script-src 'self' 'sha256-…'`。
3. 三个 vendor 库已本地化（很好），上 CSP 时不会因为 CDN 域名而被迫放宽。

### 1.7 [P2] 其它安全逻辑待补

| # | 问题                          | 位置 / 说明                                                                                                                                                                                                                                                               |
| - | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a | **管理动作无审计**                 | 删帖、删评论、禁用/删除用户、审核、增删管理员白名单，全部无留痕。出问题无法回溯。建议加一张 `admin_audit_log(actor, action, target, at, payload)`，在各 RPC 内写入。                                                                                                                                                      |
| b | **`admin_add_email` 无二次确认** | 任何管理员可把任意邮箱加为管理员；`admin_remove_email` 已防止移除自己（好），但授权方向没有对称保护。                                                                                                                                                                                                         |
| c | **`profiles.status` 客户端可写** | `profiles_own_all` 是 `FOR ALL`，用户能 `UPDATE` 自己的 `status` 列。目前靠 `is_active()` 在同一语句快照里仍读到旧值才挡住了"自我解禁"——**这是隐式依赖，很脆**：一旦有人把 `is_active()` 改成易变函数、或改用 `NEW.status` 判断，禁用即可被绕过。建议 `REVOKE UPDATE (status) ON public.profiles FROM authenticated`，或让 status 只能经管理员 RPC 修改。 |
| d | **时间字段可伪造**                 | 作者能改自己行的 `created_at`/`updated_at`，影响排序与展示。建议服务端 `DEFAULT now()` + 触发器覆盖。                                                                                                                                                                                             |
| e | **登录无失败次数限制**               | 依赖平台侧限流；`auth.js` 只做了前端 60 秒倒计时（可绕过）。建议确认平台是否对同 IP/同邮箱的密码尝试有风控。                                                                                                                                                                                                       |
| f | **忘记密码可枚举邮箱**               | `resetPasswordForEmail` 的响应差异可能暴露"该邮箱是否注册"。建议无论是否存在都返回同一提示。                                                                                                                                                                                                           |
| g | **登录页仅提示不阻断**               | `auth.js` 的 `checkOrigin()` 在域名不符时只弹提示。既然 RLS 与 Origin 强绑定，不如直接把提交按钮禁用，省得用户白填一遍。                                                                                                                                                                                      |
| h | **会话令牌在 localStorage**      | 这是 SDK 行为，配合 1.1 的 XSS 可被窃取。修好 XSS 是主要手段，其次可考虑缩短会话有效期。                                                                                                                                                                                                                |
| i | **图片/外链无隐私兜底**              | 内容里的 `<img srcset>`（见 1.1 漏项）可作追踪像素，泄漏读者 IP/UA。若要收敛，可在渲染时统一改写外链图片，或至少加 `referrerpolicy="no-referrer"`。                                                                                                                                                                |

**做对的地方，值得保留**：服务端边界（RLS + `SECURITY DEFINER`）与前端守卫分层清晰；`guardAdmin()` 注释明确写了"真正的边界在数据库"；`auth.js` 的 `nextUrl()` 做了开放重定向防护；`is_active()` 被统一加进所有写策略的 `WITH CHECK`；`admin_users`/`admin_posts`/`admin_stats` 等函数内部都自校验 `is_admin()`；`admin_users` 以 `auth.users` 为主表并做 project 兜底，注册未建资料的账号也能被管理。

## 2. 功能缺口（合流完成后新暴露的）

### 2.1 [P0] 云文章发布后不触发重建，搜索/RSS/sitemap 会陈旧

`cloudposts.py` 只在**构建期**拉取已发布文章并合流；`.github/workflows/deploy.yml` 的触发条件只有 `push` 和 `workflow_dispatch`。

**结果**：管理员在后台发布一篇文章，`post.html?slug=` 立刻可读（客户端渲染），但**首页统计、站内搜索、`feed.xml`、`sitemap.xml`、标签页要等下一次 `git push` 才会更新**。订阅者收不到更新、搜索不到新文、搜索引擎也发现不了——合流做了，但缺一个"发布即重建"的扳机。

**建议**：后台发布/审核通过后，调用 GitHub `repository_dispatch`（或 `workflow_dispatch` REST）触发一次 Actions 重建；再用 `schedule` 每天兜底跑一次（防止有人绕过前端直接写库）。

### 2.2 [P0] 云端文章详情页对爬虫是空壳

`post.html?slug=xxx` 是纯客户端渲染，`sitemap.xml` 收录了这个 URL，但爬虫拿到的是空壳；JSON-LD 只存在于构建期生成的静态文章页（`build.py` 第 343–348 行）。等于给搜索引擎提交了一批无内容、无结构化数据的页面。


**建议**：与 2.1 合并解决——发布时重建，让云文章同时落一份**静态详情页**（`posts/<slug>.html`），客户端渲染仅作为兜底。这样顺带统一了两套 URL 风格（现在是 `posts/xxx.html` 与 `post.html?slug=` 并存）。

### 2.3 [P0] Google Fonts 在大陆不可达

`layout.py` 第 352–354 行硬依赖 `fonts.googleapis.com` / `fonts.gstatic.com`。在大陆网络下这两个域名会超时/被重置，而这两行在 `<head>` 里是**阻塞渲染**的——首屏可能白屏数秒才退回系统字体。之前已经把 marked/highlight/CDN SDK 本地化过，字体是漏网的一个。

**建议**：下载 Inter / JetBrains Mono 的 woff2 子集放到 `src/assets/fonts/`，改 `@font-face` + `font-display: swap`；或直接改用系统字体栈（中文站点收益更明显）。

### 2.4 [P1] 后台与列表的硬上限会随内容增长失效

| 位置                             | 上限           | 影响                 |
| ------------------------------ | ------------ | ------------------ |
| `admin_posts()`                | `LIMIT 300`  | 超过后旧文章"消失"，且无分页/搜索 |
| `admin_users()`                | `LIMIT 500`  | 同上                 |
| `admin.js` 评论加载                | `limit(300)` | 同上                 |
| `cloud-posts.js` 列表            | `limit(60)`  | 第 61 篇起前台看不到       |
| `write.js` / `account.js` 我的投稿 | 50 / 30      | 同上                 |

**建议**：至少给文章列表与评论区加"加载更多"（按 `created_at` 游标），或在后台加筛选/搜索。

### 2.5 [P1] 互动与内容生产力的剩余缺口

- **评论通知**：有人评论/回复，站长与作者仍收不到任何提醒（上一版 P0 的最后一块，只做了楼中楼与 PV）。可先做"文章有新评论 → 邮件通知站长"。
- **列表页无互动数**：`posts.html` 的卡片上看不到点赞/评论数，看不出热度。
- **草稿自动保存**：编辑器无 localStorage 兜底，误关页面即丢稿。
- **封面图 / `og:image`**：`layout.py` 声明了 `twitter:card: summary_large_image` 却没有 `og:image`（静态文章页才有），分享到社交平台是白板。
- **图片压缩**：`upload.js` 原样上传，8MB 的手机照片直接进正文，首屏很重。
- **定时发布**：`published_at` 字段在，但后台只能立即发布。
- **用户公开主页**：`profiles_read_all` 已开，只差一个页面（可复用已有的卡片样式）。

### 2.6 [P2] 工程与运维

- **自动化测试未进 CI**：`.preview/` 下有 `auth-flow-test.mjs`、`comment-thread-test.mjs`、`mirror-redirect-test.mjs`，但 workflow 只 `pip install` + `build`，不跑测试、不跑 lint、不查死链。
- **前端错误无上报**：线上 JS 报错（比如这次 `marked` 流最坏情况下）无人知晓。
- **无访问分析**：只有一个可被刷的 PV。
- **备份**：云数据库与 `content/` 无定期导出。
- **`.preview/` 仓库卫生**：堆了十多个 Chrome profile 与截图（已 gitignore，但建议定期清）。
- **站点配置仍是占位**：`site.config.json` 里 `social` 的邮箱还是 `mailto:your@email.com`，作者/职位信息也是占位；`content/projects/ws-blog.md` 的技术栈仍写着 Node.js（实际是纯 Python）。
